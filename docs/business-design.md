# 微信操作与运营服务 · 业务设计（讨论稿 v0.1）

> 本文是**业务设计讨论稿**，不是实现方案。目标：定清业务边界、能力清单、角色拆分、架构骨架、风控合规，以及待拍板的关键决策。全篇区分「**[协议给]**」（企微协议 API 直接提供的底层动作）与「**[自建]**」（协议给不了、必须我方服务侧实现）。设计范式参考 `~/codes/aidcp/`。

## Context（为什么做这个）

要做一个**微信操作与运营服务**：承接其他系统推送来的「给客户 X 加微信」指令 → 自动发起加好友 → 加成功后自动与客户对话。**对话内容由外部 AI 对话服务生成**（我们对它输入客户消息/上下文、消费它输出的话术），本服务只负责**微信侧的操作与运营**（收发、加友、群、朋友圈）+ **运营编排** + **风控合规**。载体是「企微协议 SAAS API」（`wework.apifox.cn`，协议/hook 级、非官方开放 API，操作的是企业微信号添加个人微信客户为外部联系人）。

设计上大量借鉴 AIDCP 的成熟范式，因为微信本质就是事件流（来消息/被加/群里有人说话/朋友圈互动），AIDCP「看一条想一下」的事件驱动多角色接力比在浏览器域更契合。

## 1. 业务定位与边界

**一句话定位**：微信「操作层 + 运营编排层 + 风控合规层」的执行中枢——承接外部加微/运营指令，把外部 AI 生成的话术在微信侧「发得像真人、发得合规、并确认真送达」，同时统一管账号健康。**我们是用户 ↔ 外部 AI 的中转站，对话记忆由我们存；对话智能外置，我们不产内容、只管记忆/路由/手脚/编排。**

| 我们负责 | 我们不负责（外部 AI / 外部系统） |
|---|---|
| 微信侧收发一切消息与媒体、加好友、群、朋友圈的原子操作 | 生成对话内容、意图理解主体、知识库 RAG |
| 加友/发消息的风控频控、养号、封号防护、账号健康 | 决定「该加谁」（获客线索由外部系统下发） |
| 拟人化节奏（何时回、拆几条、打字时长、加友间隔） | 长期记忆、知识库、话术策略的沉淀 |
| 会话路由、去重、幂等、状态机、后置校验（真送达/真通过） | SOP 业务规则设计（我们执行，策划在外部） |
| **对话记忆存储（中转站权威记录）**、原始事件流、身份/路由/去重状态（客户画像/标签投影二期） | 知识库/长期业务知识（外部 AI）、商机/订单等 CRM 深水区 |
| 账号级/异常告警（掉线/风控/AI 回不上）；人机接管二期 | 人工坐席话术（一期无转人工） |

**与外部 AI 对话服务的接口边界（已定：异步回调 + 我们是中转站存对话记忆 + 纯全自动）**
- **定位**：**我们是用户 ↔ 外部 AI 的中转站**——所有消息都经我们流转并**由我们持久化存储对话记忆**。外部 AI 负责「生成话术」，我们负责「记住、路由、控频、发送」。
- **对接形态**：异步回调。入站消息 →（POST 给 AI 服务，带 conversation_id + 归一化客户消息 + **我方上下文投影** + 事件信号）→ AI 算完**回调**我们的 endpoint（带 conversation_id + 话术序列 + reply_id）→ 过风控闸 + 拟人节奏 → 发出。回调需幂等（reply_id 去重）。
- **我们给它输入**：conversation_id、归一化客户消息、**最近 N 轮上下文/摘要（我方存储供给）**、事件信号（加友通过/被删/进群）、账号人设标识。
- **我们消费它输出**：话术文本 + 媒体发送建议。（转人工建议、标签抽取一期不消费，留二期缝。）
- **状态边界**：**对话记忆由我们存**（中转站职责，权威记录）；**外部 AI 只负责生成**，其自身是否有状态对我们透明——我们始终能供上下文，故换供应商/AI 掉线不丢历史。知识库/长期业务知识仍归外部 AI。
- **红线**：节奏与风控最终裁决权在我们；AI 想连发 5 条而风控只允许 2 条时我们截断；AI 超时/空/违规**绝不假发**（一期无转人工，改为挂起 + 告警运营 + 如实记「内容未就绪」）。

**⚠️ 我们持有两类状态**：① **对话记忆**（消息全量历史 + 上下文投影，中转站权威记录，供 AI + 运营 + 审计）；② **运营/路由/幂等状态**（链路正确性地基）：会话路由映射（conversation_id ↔ 微信号 ↔ 外部客户）、消息去重水位（appinfo）、加友任务状态机、送达/撤回回执态、风控计数与账号健康、身份稳定化（wxid 主键）。

## 2. 端到端主流程（闭环）

```
外部「给客户X加微信」指令
  → [受理] 校验/归一/去重(已好友?已pending?黑名单?) —无效则如实拒(不静默)
  → [选号] 按号龄/当日加友配额/垂类 → 归属某微信号
  → [加友风控闸] canDo('add'):配额/通过率/时间窗/账号态 —拒则背压(不扣预算不假成功)
  → [发起加友] 执行端调 add_*，叠拟人间隔 preAddDelayMs
  → [后置校验] op.result 确认"请求真发出" → 标 pending
  → [等待通过] 靠 FriendChange(2131)+sync_contact 事件/轮询确认 —超时判失败(换号/隔日重试)
  → friend.accepted → 开"新联系人会话上下文"
  → [首触] 外部AI取开场白+人设模板 → 拟人节奏 → 发送(绝不秒发)
  → ┌── 多轮对话主循环 ──────────────────────────────┐
     │ 收消息→归一→意图/情绪判定                        │
     │  ├ 高意向/投诉/要真人 → 转人工闸                  │
     │  └ 常规 → 外部AI取回复(超时/空→兜底或挂起,绝不假发)│
     │        → 拆条/去AI味 → 消息风控闸 → 节奏(读延迟/打字/条间隔)│
     │        → 发送 → 送达/撤回/被删校验 → 意向&标签回写画像│
     └────────────────────────────────────────────────┘
  → [SOP跟进] 时间驱动(Day1案例/Day3优惠/静默N天召回) → 复用对话链
  → [运营层] 群运营 / 朋友圈 —— 二期
  → [全程贯穿] 风控状态机(单写) + 异常巡视 + 账号在线自愈 + 作息窗闸
```

核心心智：与 AIDCP「看一条笔记想一下再点赞」同构——这里是「看一条微信事件，想一下再决定回什么、什么时候回、要不要转人工」。

## 4. 角色拆分（核心交付：模拟人处理微信事件的多角色接力）

设计原则：**一角色一微决策**，经 EventBus 接力，覆盖「加微→加上→打招呼→多轮→跟进→打标→群/朋友圈→异常巡视」全生命周期。约 40 角色，与 AIDCP 的 32–37 同量级、分类一一对应。标 **[MVP]** 者为一期必需。

**类别一 · 加好友闭环（获客）**
- FriendRequestIntake **[MVP]**：受理外部加微指令 → 校验/去重/选号 → `add.candidate`
- AddChannelResolver **[MVP]**：定加友渠道(手机号/群/名片)+申请语 → `add.planned`
- AddFriendRiskGate **[MVP]**：canDo('add')，准→`add.authorized`(带 preAddDelay)，拒→背压
- AddFriendExecutor **[MVP]**（执行端）：出站 `friend.add`
- FriendRequestVerifier **[MVP]**：`op.result` 确认真发出，标 pending，失败到顶升级
- InboundFriendReviewer **[MVP]**：被动加友受理，判自动通过/挂人审

**类别二 · 通过后首触（破冰）**
- FriendAcceptedWatcher **[MVP]**：`friend.accepted` → 开会话上下文 → `first_touch.needed`
- GreetingComposer **[MVP]**：调外部 AI + 人设模板 → `reply.ready`（空不发）
- FirstTouchPacer **[MVP]**：绝不秒发招呼，加拟人延迟

**类别三 · 多轮对话闭环（主战场）**
- MessageIngest **[MVP]**：`message.received` 归一(含语音转写)+appinfo 去重 → `msg.ingested`
- ConversationStore **[MVP]** ★：**对话记忆权威存储**（中转站职责）——持久化全量消息历史、维护每联系人上下文投影(最近 N 轮/摘要)，供 DialogBrainProxy 供给 AI + 运营 + 审计
- ContactRoutingRegistry **[MVP]**：会话路由(conversation_id↔账号↔外部客户)、appinfo 去重水位、加友/送达态
- DialogBrainProxy **[MVP]** ★：外部 AI 唯一收口，**异步回调**；请求时附我方上下文投影；超时/空/违规→挂起+告警，绝不假发
- ReplyComposer/Splitter **[MVP]**：长回复拆条、去 AI 味、配媒体
- MessageRiskGate **[MVP]**：canDo('message')，敏感词/配额/账号态，拒→挂起
- ReplyPacer **[MVP]**：readDelay/typing/interMsg 中心值
- SendExecutor + SendVerifier **[MVP]**：出站发送 + 校验真送达/被撤回/被删
- ~~HumanHandoffGate~~ → **二期**（一期纯全自动无转人工；见 §8 残留风险）

**类别四 · 跟进/SOP（时间驱动，二期）**
- SopScheduler：cron+阶段变化 → `followup.needed`
- FollowupComposer：外部 AI + SOP 模板 → 复用对话链

**类别五 · 标签与画像（全部二期——一期无 SOP/转人工消费意向；对话原文已由 ConversationStore 存，结构化画像二期再抽）**
- IntentClassifier / TagExtractor / TagWriter+Verifier / CustomerProfileStore —— 二期；届时可由外部 AI 回传标签建议、我们经协议 `label_*` 写回并校验

**类别六 · 群运营（二期）**
- GroupEventWatcher / GroupMessageTriage / GroupResponder / WelcomeNewMember / GroupMemberManager / GroupRiskGate —— 大部分群消息「看一眼不接话」，只挑 @我/关键词/求助响应；群务过风控闸

**类别七 · 朋友圈（支线，二期起）**
- MomentsPlanner / MomentsPublisher+Verifier / MomentsInteractionPatrol / MomentsCommentResponder —— 发布走人审；互动低频拟人（兼养号）

**类别八 · 会话守护（账号守护，MVP 必需子集）**
- AccountSessionMonitor **[MVP]**：单场预算/时长到顶收敛
- ActiveWindowGate **[MVP]**：作息窗外只被动接待
- LoginReviveAgent **[MVP]**：掉线重连/失败飞书通知扫码，期间阻塞下发

**类别九 · 巡视与风控（MVP 必需子集）**
- AnomalyPatrol：扫超时未回/AI 掉线积压/异常联系人；软中断 fail-open
- RiskSignalCollector **[MVP]**：归一风控信号喂 RiskController（不自改状态）
- RiskController **[MVP]** ★：唯一写者，四态迁移+配额+养号+作息+去重
- AlertNotifier **[MVP]**：飞书卡片

**单条私聊消息处理时序（一期：异步回调 + 无转人工）**
```
执行端(微信网关)                       决策端(RoleDispatcher + EventBus)                外部AI
 message.received ────────────────►  Ingest 归一+去重 → ConversationStore 存记忆+取上下文
                                      DialogBrainProxy ─(conversation_id+客户消息+上下文)──────► AI 算话术
                                                       ◄───(异步回调: conversation_id+话术+reply_id)─┘
                                      ReplyComposer 拆条/去AI味 → MessageRiskGate(拒→挂起/告警)
                                      ReplyPacer 算 readDelay/typing/interMsg
 message.send(序列,带节奏) ◄────────  命令桥翻译, 定向回该账号连接
 send.receipt(送达/撤回) ───────────►  SendVerifier 校验真送达/撤回/被删; 失败到顶→升级+RiskSignal
 (AI 超时未回调) ··················►  AnomalyPatrol 扫积压 → AlertNotifier 告警运营(无系统内转人工)
```

## 4.5 运营驱动模型（系统如何主动运营）

> 核心命题：**运营 = 主动动作**。「系统如何驱动运营」= 是什么让系统主动做事、按什么优先级、受什么约束、如何像人一样有节奏。对话主链是**被动反应**（收到才回）；运营是**主动**（自己决定今天做什么）。

**五个驱动源（触发系统做事的来源）**
| 驱动源 | 触发什么 | 形态 | 阶段 |
|---|---|---|---|
| ① 外部指令驱动 | 外部系统推「加微/群发/发圈」指令 | 命令式触发器 | MVP(加微) |
| ② 入站事件驱动 | 客户消息/加友通过/被删/进群/朋友圈互动 | 事件总线角色(反应式) | MVP(对话) |
| ③ 时间驱动 | SOP 定时跟进、静默召回、朋友圈排期、群日历、养号任务 | 每分钟心跳调度器 | 二期 |
| ④ 状态驱动 | 客户阶段迁移(新客→意向→成交→流失)、账号健康降档、风控迁移 | 状态机 + 心跳 | 二期 |
| ⑤ 巡视驱动 | 定期扫「该做没做」:超时未回、AI 掉线积压、长期无跟进的高意向、异常 | 定时巡视(兜底自驱) | MVP(轻量) |

**两种触发器形态（直接搬 AIDCP 的关键区分）**
- **事件驱动角色**（走 EventBus，反应式，"看一条想一下"）：对话主链、加友闭环、巡视。
- **命令式心跳调度器**（云端单进程、每分钟心跳、**不进角色注册表、不走事件总线**）：时间驱动的运营（SOP/朋友圈排期/群日历/养号）。AIDCP 的 content-scheduler 正是如此——时间驱动是"扫全账号、按闸触发"，不塞进事件总线。
- **被动对话用事件总线，主动运营用心跳调度器**；两者产出的动作汇入同一条下游管道。

**统一下游管道（设计优雅点：驱动源可插拔，管道单一）**
无论哪个驱动源，产出的都是一个"待发意图"，统一流经：
```
意图 → 组装(拆条/去AI味/配媒体) → 风控闸 canDo → 拟人节奏(readDelay/typing/interMsg/preAddDelay)
     → 执行端发送 → 后置校验(真送达/真通过) → 回执回流
```
MVP 就把这条管道 + 三闸建好，二期挂新驱动源/新角色是"加插件"，不改架构。

**运营调度中枢（Operations Scheduler，主动侧心跳引擎，对应 content-scheduler）**
- 每分钟心跳，遍历在线账号，按**闸序**判定：排期启用 ∧ 活跃时段格 ∧ 命中错峰分钟 ∧ 未达日上限 ∧ 风控 normal ∧ 过风控闸。
- **错峰**：`hash(accountId + 本地日期 + 动作) % 60` 得分钟偏移（纯函数、逐日变、账号间错开）。
- **幂等 + 重入护栏**：`(账号,动作,时间格)` 不重复触发；上轮未完跳过本轮。
- **fail-closed**：未配即不自动（绝不 fail-open 把没配的账号当"随便发"）。
- **自动时窗 ⊆ 活跃时段**：休眠格绝不主动（深夜准点群发是强机器信号）。
- 产出运营任务（`followup.needed`/`moments.needed`/`group.sop.needed`/`nurture.needed`）注入下游管道。

**像人一样驱动：优先级 + 预算 + 作息（模拟人运营）**
- **作息窗**（weekly-active-window）：非活跃时段不主动；被动接待可放宽但也收敛（凌晨秒回也是机器信号）。
- **预算**：每账号每日主动动作预算（加友/群发/发圈/主动首触），**主动预算远紧于被动回复**。
- **优先级（冲突解决）**：被动回复 > 主动跟进（别晾客户）；高意向跟进 > 泛化群发；风控降档时**先砍主动、保被动**。
- **节奏 + 疲劳**：动作间拟人间隔，越做越"累"。

**关键红线（搬 AIDCP）**
- 主动高风险动作（群发/发圈/批量加友）**默认走人审提议**（content-schedule「只提议绝不自动发送」）或至少最严风控闸；二期上群发/朋友圈时人审闸必接上。
- 主动 ≠ 无节制：所有主动动作过 canDo + 作息 + 预算三闸，任一不过**诚实不做**（不排队重试形成卡点）。
- 配额背压 ≠ 风控信号：撞自己主动预算只是今天不做，不自升风控态。

**闭环自驱动**：动作结果（送达/通过/回复/被删/被举报）回流 → 更新客户状态(阶段/活跃度) + 账号健康 → 影响下一轮心跳该驱动什么。今天发的跟进有没有回复，决定明天升级触达还是转召回——运营"自己滚起来"。

**MVP vs 二期的驱动边界**
- **MVP 驱动源**：①外部指令(加微) + ②入站事件(对话) + ⑤轻量巡视(兜底)。主动动作只有"加友后首触"这一个半主动。
- **二期**：接上 ③时间驱动 + ④状态驱动（心跳调度器 + 客户阶段机 + SopScheduler/群/朋友圈角色），运营才真正主动滚起来。
- **MVP 必须留好三条缝**：统一下游管道（所有动作汇入）、运营调度中枢骨架（哪怕只挂巡视）、预算/作息/风控三闸（阈值可宽松但要在）。二期是加插件，不是改架构。

## 4.6 运行时并发与调度模型（多客户 / 异步等待 / 抢发 / 驱动优先级）

> 贯穿约束：**一个账号对外 = 一个人在操作一部手机**。会话之间可高并发，但同一账号的对外动作必须串成一条自然时间线。下面四问都服从这条。

**(1) 多客户并发：按会话分片、片内串行、片间并发**
- **每 (账号, 客户) 会话 = 一个逻辑 actor**（继承 multi-tenant「每连接一束上下文」，粒度细化到客户）。片内 FIFO 串行（第 2 条不抢在第 1 条前回），片间完全并行、不串号、互不阻塞。
- 入站归一后按 `conversation_id` 路由到对应 actor 的 inbox；`appinfo` 去重水位挡协议重推/回调重放。
- 协议不保证回调顺序（见 §1 能力缺口）→ actor 入口按 `sendtime/seq` 在防抖窗内重排 + 去重，吸收乱序。
- **有界并发 + 公平**：外部 AI 调用有每账号/全局并发上限；多客户同来走队列 + 轮转，防话痨客户饿死他人。下行定向回发起账号连接。

**(2) 等 AI 返回期间：pending 待回态 + 请求代号 + 超时，不阻塞**
- 发出请求后会话进 `awaiting_ai`，带单调 `requestId`（correlation key）。异步回调形态：发完即释放，不占线程干等。
- 挂**超时定时器**（如 30–60s）：超时→红线兜底（挂起 + 告警运营 + 记「内容未就绪」，绝不假发；可选一次幂等重试）。
- 回调按 `requestId + reply_id` 匹配 + 幂等去重；匹配不上/过期的回调**丢弃**。
- **AI 时延被拟人延迟吸收**：发送时刻 = max(AI 返回时刻, readDelay 下限)——AI 太快也不早发。
- **回来后再过闸**：发送前重过风控 + 目标存活（没被删/账号在线）+ 新鲜度检查，不是拿到话术就无脑发。
- pending 可被 AnomalyPatrol 巡视扫到，超时积压能被发现。

**(3) 等待期间客户又发消息：防抖聚合 + 代号作废（像等人说完）**
- **洞察**：人发微信是「多气泡」——一句拆几条连发；真人会等对方发完再回。
- **入站防抖/聚合窗**：收到消息不立即请求 AI，等一个静默窗（如 2–5s）；窗内又来则**合并成一批**再一次性请求。既省调用又拟人。窗口 = min(静默 Δt, 最大等待 T)（有上限，不无限等）。
- **AI 请求已在途、客户又发新消息** → **代号作废重来（supersede）**：递增 `requestId`，把在途的标记过期；用合并后新上下文重新发起。旧回调回来时代号不匹配 → **丢弃**（基于不完整输入的话术会答非所问）。对应 AIDCP「新鲜度/epoch 守卫」。
- **最后一刻新鲜度检查**：即便未作废，发送前若发现期间客户又说话 → 默认以最新输入为准，旧话术降级/丢弃。
- 保证回复逻辑顺序，绝不回复错位；合并批次用 appinfo 集合标识防重复并入。

**(4) 多驱动器优先级：每账号「行动仲裁器」+ 优先级队列 + 共享节奏时钟**
- 所有驱动源（§4.5 五源）产出的待发意图**不直接发**，进**每账号优先级队列**；一个仲裁器按 优先级 → 预算 → 节奏 → 风控 出队。
- **优先级（高→低）**：① 登录态/风控自愈（保命）② 被动对话回复（别晾客户）③ 加友后首触（趁热）④ 高意向/状态驱动跟进 ⑤ 时间驱动 SOP/召回 ⑥ 泛化群发/朋友圈（最低、最高风险）⑦ 养号/巡视（填空隙）。
- **抢占 = 间隙让路，不硬打断**（对应「临时离开式 vs 阻塞式打断」）：高优先级在低优先级动作的自然间隙插入，不腰斩半截动作。唯一阻塞式硬闸 = 风控/验证码/掉线，可立即暂停下发。
- **预算**：每账号每日总行动预算先保高优先级（被动回复），剩余给主动；风控降档时**主动预算先归零、被动保留**。
- **共享节奏时钟**：仲裁器出队后仍过节奏闸，同账号不同一秒并发多动作——把内部并发收敛成「一个人操作一部手机」的单线时间线。作息窗：主动受限，被动窗外也收敛。

**单会话回复状态机（Q3 详图：防抖 + 异步 AI + 代号作废）**
```
   ┌──────────────────────────────────────────────────────────────────┐
   ▼                                                                    │
[idle] ──客户消息──► [debouncing]（收批 batch, 静默计时 Δt, 上限 T）     │
                        │  ▲ 窗内又来：并入 batch, 重置 Δt（≤T 触顶）     │
   ┌────────────────────┘                                               │
   │ 静默 Δt 到 / 触顶 T                                                 │
   ▼                                                                    │
[awaiting_ai] ── requestId=k, POST(batch+上下文)给AI, 启超时 ──►（AI 算） │
   │  │                                                                 │
   │  └─客户又发消息─► 作废 k(标 stale), requestId=k+1, 回 [debouncing] ─┘
   │
   ├─ 回调(id=k, 新鲜) ─► 新鲜度✔ + 风控✔ + 目标存活✔ ─► [ready_to_send]
   ├─ 回调(id≠当前/过期) ─► 丢弃, 原地
   └─ AI 超时 ─► 挂起 + 告警运营 + 记「内容未就绪」(可选1次幂等重试) ─► [idle]

[ready_to_send] ─► 共享节奏时钟(readDelay/typing/interMsg) ─► 执行端发送
                ─► 送达/撤回校验 ─► 存记忆/回执 ─► [idle]
                └─ 发送前闸失败(风控/被删) ─► 挂起/丢弃 + 记录
  （AnomalyPatrol 定时扫描超时仍停在 awaiting_ai 的会话 → 告警兜底，不静默漏）
```

## 5. 架构骨架（三层）

```
┌─────────────────────────────────────────────────────────┐
│ 决策端(云重)：编排+风控+运营大脑                            │
│  EventBus · RoleDispatcher · RiskController(单写)         │
│  ConversationStore(对话记忆·中转站权威) · RoutingRegistry  │
│  SopScheduler · CommandBridge(命令桥) · AlertNotifier      │
├─────────────────────────────────────────────────────────┤
│ 对话对接层：DialogBrainProxy                               │
│  外部AI唯一收口：超时/熔断/降级/内容合规校验/可观测         │
├─────────────────────────────────────────────────────────┤
│ 执行端(边轻)：微信协议网关 + 通道适配层                     │
│  通道适配层(企微/个微抽象) → 协议API提供方                  │
│  归一化回调为标准入站事件 · 执行原子操作 · 即时本地校验      │
│  拟人抖动落地(云端给中心值,边缘叠随机+下限+断连兜底) · 不做决策│
└─────────────────────────────────────────────────────────┘
```

**与 AIDCP 边云模型的异同**
- **原样搬（AIDCP 值钱的一半）**：边轻云重、事件驱动多角色、风控状态机单写、绝不静默假成功、拟人节奏收口云端、多租户每连接一束上下文、会话恢复/作息窗、OpenSpec 规范、飞书人审卡片。
- **删（整层 DOM 定位复杂度）**：语义锚点/AnchorCache/matcher 消歧/CDP/jsdom/浏览器指纹反检测——微信目标有稳定 ID(wxid/roomid)，不存在「点错元素」，砍掉约一半复杂度。
- **反检测元原则保留、手段换域**：从「浏览器指纹自洽」→「一号一设备/一 IP/一登录环境长期稳定」。
- **反污染换靶**：AIDCP「LLM 锚点先暂存后晋升」→ **联系人身份稳定化**（先只有昵称、后拿 wxid，确认稳定才作主键，防合并/拆分画像）。
- **新增对话对接层**：外部 AI 是 AIDCP 没有的新边界，等价于「内容大脑 LLM」但托管在外，当「会超时/会空返回/会违规的依赖」治理。

## 6. 风控与合规（生死线）

**频控与养号（按动作分档，加友最严）**
| 动作 | 养号档 | 正常档 | 激进档 | 备注 |
|---|---|---|---|---|
| 主动加好友 | 个位数/天 | 中 | 高(仍远低于人直觉) | **头号封号源**，与被动接待完全解耦档位 |
| 被动通过好友 | 低 | 中 | 高 | |
| 群发/批量触达 | 0 | 严格限 | 限 | 新号未养严禁群发 |
| 朋友圈发布 | 0-1 | 1-2 | 数条 | 3 天养号期内不发 |

- **冷启动养号**：新号前 N 天极低频、先被动收发、完善资料、少量加友（协议明确「新设备前 3 天不建议主动加友/群发/朋友圈」）。
- **作息窗闸**：7×24 周历，非活跃时段只被动接待。
- **比例约束比绝对值更重要**：加友通过率、主动/被动消息比、群发占比实时算，异常即降档。
- **配额背压 ≠ 风控信号**（AIDCP 关键教训）：撞自己配额只背压、绝不自升状态（否则自锁）；只有平台真实信号（限流硬阻断/被拒骤增/需验证/被封）才驱动四态迁移 `normal→warned→restricted→frozen`。
- **封号防护**：一号一 IP 一设备、掉线告警+自动重连、异地登录提醒、账号健康度评分（被删率/举报/通过率异变）、连续失败到顶停手升级（无限重发本身即高危）。
- **敏感词**：发送前违禁词/链接黑名单拦截 **[自建]**（MVP 即要）。
- **一期纯全自动、无人工缓冲，风控与敏感词是唯一护栏**：敏感词/合规校验从「建议」升为「硬闸」；AI 回不上/超时时至少飞书告警运营（不能让客户被静默晾着），红线「绝不假发」不变。
- **多账号多租户**：每微信号=一连接束（独立上下文/预算/风控账号），指令定向回发不串号，身份穿透握手；跨号去重、同客户归一、按健康度分配加友任务。

## 7. 工程落地建议

- **仓库拓扑（已定）：3 个 git 仓 = AIDCP 家族去掉 edge**。不设 MVP 硬切、按可持续迭代推进：架构一次到位、能力增量交付。

  | 仓 | 角色 | 对标 AIDCP |
  |---|---|---|
  | **aiim**（控制仓） | 契约/设计/openspec/部署编排的单一真源，无业务代码；panel API 契约(服务↔后台)、微信事件/指令契约、红线不变量都在此 | aidcp |
  | **aiim-service**（服务仓，内部 monorepo） | 微信操作与运营后端 + 管理后台后端(panel API)。内部拆 apps + packages | aidcp-cloud(含 panel/) |
  | **aiim-console**（管理后台前端） | 运营 Web 控制台；只读 panel API + 经 `/api` 下发指令，**绝不直连微信网关** | aidcp-console |

  **没有 edge 仓**：微信=HTTP+webhook 服务器对服务器，无 CDP/住宅 IP/设备指纹，不需要 AIDCP 那个必须贴浏览器本地跑的 edge（AIDCP 自己的飞书 Bot 同为 HTTP+webhook、就住在 cloud 无 edge）。养号/IP/设备关切落在服务商实例层(set_proxy 配代理)+ 我方风控。**控制仓这次成立**：有 2 个代码仓(service+console)共享 panel API 契约 + 要 spec-driven openspec + 部署编排——只是比 AIDCP 轻(无边云 WS 协议 4-5 处同步)。

- **aiim-service 内部 = monorepo(apps + packages)，不再拆更多 git 仓**：
  ```
  aiim-service/
  ├── apps/
  │   ├── gateway/    # 企微 HTTP 客户端 + webhook 入站归一 + 实例连接/登录态(薄, I/O 密集, 可独立扩缩容)
  │   ├── brain/      # EventBus + RoleDispatcher + ~40 角色 + RiskController 单写 + 多租户 + 行动仲裁器 + DialogBrainProxy
  │   ├── scheduler/  # 运营心跳调度器(时间/状态驱动运营, 独立进程 cron 式)
  │   └── panel/      # 管理后台后端 API(独立端口, 供 console)
  └── packages/
      ├── kernel/     # 复制内联的 AIDCP 机制层, 泛型化(event-bus/risk/feishu/llm/pacing/humanize/soul + Envelope<TType>)
      ├── contracts/  # 微信事件/指令契约 WechatEventMap/RoleName/MessageType(wxid/roomid 寻址) + panel API DTO
      └── store/      # PG 持久化(ConversationStore 对话记忆 + 路由/去重/风控)
  ```
  gateway/brain/scheduler 用**异步事件/队列**解耦、可各自独立部署与扩缩容——这是「进程/部署拆分」而非「git 仓拆分」，避免 AIDCP 跨仓协议 4-5 处同步的税。lint 禁止 packages/kernel 反向依赖 apps/contracts，防微信契约漏进通用引擎(AIDCP 的 EventBus 就栽在 import 死了 XHS 的 AllEventMap)。

- **内核复用 = 复制内联到 packages/kernel，暂不抽独立共享库**（不是 MVP 妥协，是正确排序）：机制层对 XHS 耦合 grep≈0（event-bus/index.ts、risk-controller.ts、risk-state-machine.ts、sliding-window-counter.ts、quotas.ts、llm、feishu/messenger 命中全 0），复制+泛型化即用；humanize 三个纯函数从 aidcp-edge 复制(**切勿依赖整个 edge**，会拖进 Electron/CDP/jsdom)。抽 `@aidcp/kernel` 独立库的收益只有 ≥2 个消费者才兑现，今天只有 aiim-service 一个，且抽库要动正在生产的 aidcp-cloud——徒增风险；出现第二消费者(或要与 AIDCP 统一)再 lift-and-shift。
- **删**浏览器域遗产（DOM 定位/锚点/CDP/jsdom/指纹反检测）；**复制风控时消除三处 XHS 浅耦合**：RiskAction 动词换微信语义(add_friend/send_message/…)、重定义三档 quotas、删/换 likeRatio 护栏(like/view≤0.35)、zeroInteractions 放行动作 view→read_message。参数化即消除，别忘。
- **走 OpenSpec**：每能力 proposal→design→tasks→apply→validate→archive；跨模块/协议/风控改动先建 change。
- **事件信封复用**：`v/type/id/ts/payload`，请求-响应 id 配对，坏帧回 error；消息面替换为微信事件集（`friend.*`/`message.*`/`group.*`/`moments.*`/`account.*`/`op.result`/`send.receipt`/`risk.*`）。
- **协议四处同步 + 路由白名单回归断言**：本域同样有「新增 cloud→edge 主动命令但执行端未放行→静默丢弃」的坑，必立断言（AIDCP 踩过）。
- **核心数据模型**：微信号(guid/健康度/档位)、联系人(wxid 稳定身份+来源+画像投影)、会话上下文(按联系人/最近 N 轮/阶段)、加友任务(状态机)、消息(appinfo 去重键/送达态)、群、风控账号(四态/配额/滑窗)、原始事件流。
- **外部 AI 依赖治理**：统一经 DialogBrainProxy 收口，设超时/降级/熔断/内容合规校验 +「内容未就绪绝不假发」红线 + 调用可观测(token/时延/失败率)。

**四条红线不变量（固化到验收，对应 AIDCP 的 AC-* 套件）**
1. **三个真相时刻缺一不可**（`AC-ADD-*`/`AC-MSG-*`）：加友(回执 ok≠送达≠对方通过，靠事件/轮询确认)；发消息(回执 ok≠收到≠未撤回)；打标/群操作(写后回读)。
2. **外部 AI 诚实边界**：超时/空/违规绝不发占位或编造，挂起/兜底/转人工，如实记「内容未就绪」。
3. **后置校验+重试上限+升级**：连续失败到顶判系统性问题→停手升级置风控态，绝不无限重发。
4. **身份稳定化**（`AC-TAG-*`/`AC-RISK-*`）：wxid/roomid 先暂存确认稳定才作主键；配额背压不自升状态；被禁号 record 返 false。

## 8. 决策记录与残留风险

**已定（2026-07-07）**
1. **一期 MVP 范围** = 只跑通「加微→打招呼→多轮对话」主链；群/朋友圈/SOP/标签画像/转人工全部二期。
2. **外部 AI 接口** = 异步回调为主（发消息给 AI→回调→过闸+节奏发出，回调幂等），同步作简单兜底且必带超时降级。
3. **会话记忆** = **由我们存储**（我们是用户 ↔ AI 的中转站，全量消息历史 + 上下文投影是我方权威记录）；外部 AI 只负责生成、由我方供上下文，知识库/长期业务知识仍归 AI（见 §1）。
4. **人机协同** = 纯 AI 全自动，一期无转人工。

**⚠️ 残留风险（由上述选择引入，实现时守住）**
- **无人工缓冲**：投诉/高危/AI 答不上时无人接手。缓解：① 敏感词/合规拦截升为硬闸；② AI 回不上/超时时飞书告警运营（人可手动去微信端处理），红线「绝不假发」不变；③ 保留转人工扩展缝（HumanHandoffGate 二期直接接上、不需重构）。
- **AI 供应商耦合**（已因「记忆自持」大幅缓解）：对话历史在我方、可回放供上下文，换供应商/AI 掉线不丢记忆；仍需 DialogBrainProxy 抽象统一接口，且存储成本随消息量增长需分级留存。
- **运营可见性弱**：一期不建画像/统计 UI，运营只能靠事件流+告警。可接受（外部系统大概率自建看板）。

**已定（2026-07-07，修订）**
6. **仓库拆分** = **3 个 git 仓**：`aiim`(控制仓 docs/openspec/契约) + `aiim-service`(后端 monorepo：apps gateway/brain/scheduler/panel + packages kernel/contracts/store) + `aiim-console`(管理后台前端)。= AIDCP 家族**去掉 edge**(微信 HTTP+webhook 无边云物理约束)。不再拆更多 git 仓——gateway/brain/scheduler 是服务仓内的 apps(进程/部署拆分)，kernel/contracts 是内部 packages(非独立库，出现第二消费者再抽)。**不设 MVP 硬切**、按可持续迭代推进；管理后台(console + panel)属首批、不算二期。详见 §7。

**仍待你拍板（不阻塞一期设计）**
5. **账号规模** —— 推荐：MVP 按多账号设计（每号一连接束），先跑 1–3 号。多租户是地基不能后补。

## 9. 验证方式（进入实现后）

- **提供方能力矩阵摸底**（先决）：企微协议各家在「送达/已读/撤回回执」「能否拿 wxid 稳定身份」「群/朋友圈支持度」「被限流信号是否上报」差异巨大——后置校验红线的可实现性直接取决于此。先摸底再定哪些「真相时刻」靠回执、哪些靠轮询兜底。
- **端到端冒烟**：1 个测试企微号，走「外部指令→加友→通过→首触→多轮对话（对接外部 AI mock）→送达校验」全链路，人工观察节奏是否拟人、失败是否如实上报（不假成功）。
- **红线验收套件**：`AC-ADD-*`/`AC-MSG-*`/`AC-RISK-*`/`AC-TAG-*` 全绿方可上线。
- **风控灰度**：新号先养号档跑数天，观察加友通过率与掉线率，再逐步放量。

## 10. 实施路径（下一步）

按 AIDCP 的 OpenSpec spec-driven 流程推进；一期只交付「加微→对话主链」，但把运行时并发骨架与三闸留全。

- **工程决策（已定）**：MVP **单仓模块化单体**，内部 `packages/kernel`(复制内联 AIDCP 机制层、泛型化) ↔ `src/`(微信契约+装配)；不抽共享库/不设控制仓/不分边云仓/无 console(MVP)；按多账号设计、先跑 1–3 号。详见 §7 仓库拓扑。
- **实施顺序**：
  1. **提供方能力矩阵摸底**（先决）——落实送达/已读/撤回回执、wxid 稳定身份、被限流信号等能不能拿到，定「真相时刻」靠回执还是轮询。
  2. **复制内核内联(packages/kernel 泛型化/参数化) + 微信协议网关适配层**——归一化回调为标准入站事件、执行原子操作、通道适配(先做企微协议一种、留个微缝)。
  3. **加友闭环**——受理→选号→风控闸→发起→后置校验→等通过(2131+sync_contact)→超时判失败。
  4. **对话主链**——按会话分片 actor + 防抖聚合 + 异步回调 pending/代号作废 + 组装/风控闸/拟人节奏/发送/送达校验；ConversationStore 存记忆、DialogBrainProxy 收口外部 AI。
  5. **风控账号中枢 + 多租户 + 行动仲裁器**——四态状态机单写、配额/养号/作息、每账号优先级队列 + 共享节奏时钟。
  6. **红线验收套件** `AC-ADD-*`/`AC-MSG-*`/`AC-RISK-*`——全绿。
  7. **端到端冒烟 + dev 灰度养号**——1 号真机走全链路(AI 用 mock)，再养号档灰度放量。
- **二期接入点**（架构已留缝，属加插件）：时间/状态驱动的运营调度中枢（SopScheduler/心跳）、群运营、朋友圈、标签画像、转人工闸。
