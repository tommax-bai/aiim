# AIIM

**AIIM**（微信操作与运营服务）——承接外部系统推来的「给客户加微信」指令：自动发起加好友 →
加成功后由**外部 AI 对话服务**（异步回调）提供话术 → 我们负责微信侧收发与运营，并统一管账号风控。

> **一句话定位**：我们是用户 ↔ 外部 AI 的**中转站**——存对话记忆、管微信操作与运营、控风控。
> 对话智能外置，我们不产内容、只管记忆/路由/手脚/编排。

设计范式借鉴 [AIDCP](../aidcp)：事件驱动多角色 + 风控状态机单写 + 绝不静默假成功 +
拟人节奏收口 + 多租户；**删掉浏览器 DOM 定位那一整套**（微信目标有稳定 wxid/roomid，不需要定位）。

## 仓库家族（3 仓 = AIDCP 家族去掉 edge）

| 仓 | 角色 | 对标 AIDCP |
| --- | --- | --- |
| **aiim**（本仓，控制仓） | 契约 / 设计 / openspec / 部署编排的单一真源，**无业务代码** | `aidcp` |
| **aiim-service**（`../aiim-service`） | 微信操作与运营后端 + 管理后台后端(panel API)；内部 monorepo(apps + packages) | `aidcp-cloud` |
| **aiim-console**（`../aiim-console`） | 运营 Web 控制台；只读 panel API + 经 `/api` 下发指令，**绝不直连微信网关** | `aidcp-console` |

**无 edge 仓**：微信是 HTTP + webhook 的服务器对服务器集成，无 CDP / 住宅 IP / 设备指纹，
不需要 AIDCP 那个必须贴着浏览器本地跑的 edge（AIDCP 自己的飞书 Bot 同为 HTTP+webhook、就住在 cloud 无 edge）。
养号 / IP / 设备关切落在协议服务商实例层（`set_proxy` 配代理）+ 我方风控。

## 设计主张

1. **逻辑三层、物理一体**：执行端(微信协议网关) / 对话对接层(DialogBrainProxy) / 决策端(编排+风控)
   是**代码分层不是部署分仓**；服务仓内以 `apps/gateway`、`apps/brain`、`apps/scheduler`、`apps/panel` 承载，异步事件解耦、可各自扩缩容。
2. **事件驱动多角色**：模拟人处理微信事件，一角色一微决策，经 EventBus 接力（约 40 角色，覆盖
   加微→通过→首触→多轮对话→跟进→打标→群/朋友圈→异常巡视全生命周期）。
3. **风控状态机单写**：账号健康 `normal→warned→restricted→frozen` 只由云端 `RiskController` 写；
   配额背压 ≠ 风控信号（撞自己配额只降速、不自升状态）。
4. **绝不静默假成功**（红线）：加友「API 回执 ≠ 送达 ≠ 对方通过」、发消息「回执 ≠ 收到 ≠ 未撤回」，
   都要后置校验；外部 AI 超时/空/违规**绝不假发**。
5. **中转站存记忆**：对话历史在我方（权威记录），外部 AI 只负责生成、可换供应商、可掉线不丢历史。
6. **拟人节奏收口 + 多租户 + 行动仲裁器**：把内部并发收敛成「一个账号对外像一个人在操作一部手机」。

## 端到端主流程

```
外部「给客户X加微信」→ 受理/去重/选号 → 加友风控闸 → 发起加友 → 后置校验(请求真发出)
→ 等通过(FriendChange 2131 + sync_contact) → 首触(外部AI, 绝不秒发)
→ 多轮对话(收消息→防抖聚合→外部AI异步回调→拆条去AI味→风控闸→拟人节奏→发送→送达校验)
→ 跟进/SOP/群/朋友圈(运营驱动) → 全程贯穿风控状态机 + 异常巡视 + 掉线自愈
```
